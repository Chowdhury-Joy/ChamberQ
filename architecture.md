# Architecture Overview
Last Updated: 2026-08-13T10:46:29+0600

## Overview
ChamberQ (product formerly "Doctor Gemini") is a multi-tenant SaaS for Bangladesh solo doctors and clinics. Each tenant can be sold **à la carte product modules** on top of a Solo/Clinic size tier: **Front door** (branded website + online serial booking + day list), **Live queue** (outdoor TV + Call next + ticket come-around), and **Prescription** (consult pad / digital Rx). Modules default on for existing chambers. Patients book a serial and pay at the chamber — there is no payment gateway. Online pre-payment is later-stage only: do not suggest or build it unless the owner explicitly asks. **Two booking doors:** the doctor's own website (name + phone, no account) and optional ChamberQ **Find a doctor** (`/find`) plus phone-OTP **Patient login** (`/me`) for one locker of serials and history across every Front door clinic. Sales CTAs on the central marketing site use WhatsApp (`wa.me`). Patient outbound notices (booking confirmation, doctor late, cancellation, prescription link) follow each doctor's `notify_channels` mix of prepaid SMS and/or human-tapped WhatsApp; Super Admin tops up the tenant SMS wallet. Marketer partners earn commissions on setup and monthly subscription fees (manual bKash billing); Super Admin confirms doctor payments and marketer payouts.

## Getting Started
Prerequisites: PHP 8.3+, Composer, Node/npm (for Vite assets), SQLite (local) or MySQL/Postgres (production). `composer.json` pins `config.platform.php` to `8.3.0` so dependency resolution matches the live host even when a developer laptop runs a newer PHP.

```bash
composer install
cp .env.example .env
php artisan key:generate
touch database/database.sqlite   # if using sqlite
php artisan migrate --seed
php artisan catalogues:load   # required — migrations create empty tables; this imports ~24,491 medicine SKUs + ~244 conditions (takes ~12s)
npm install
npm run build
php artisan serve
```

Optional: `composer run dev` (server + queue + Vite + logs).

Key environment variables (names only): `APP_KEY`, `APP_URL`, `APP_TIMEZONE`, `CENTRAL_DOMAINS`, `DB_*`, `MAIL_*`, `MARKETING_WHATSAPP`, `MARKETING_PHONE`, `MARKETING_SOLO_*`, `MARKETING_CLINIC_*`, `MARKETING_SMS_CREDIT_PRICE`, `SMS_DRIVER`, `SMS_ENABLED`, `SMS_HTTP_URL`, `SMS_HTTP_API_KEY`, `SMS_HTTP_SENDER`.

Production must set `APP_URL=https://…` (not localhost — path-tenant SMS/outbound links are built from it) and `CENTRAL_DOMAINS` to the real public host(s). Patient-facing absolute links that leave the browser (SMS, WhatsApp, TV bookmark, ticket Copy link) go through `TenancyUrl::publicAbsolute()` (Domain or `APP_URL`). Same-origin navigation and polls use relative paths / `public_asset()`. `bootstrap/app.php` also trusts reverse proxies (`trustProxies(at: '*')`).

Local URLs:
- Central marketing + Super Admin: `http://localhost/` and `http://localhost/admin`
- Marketer partner panel: `http://localhost/partner`
- Platform tenant (path tenancy): `http://localhost/solo/` (book at `/solo/book`, admin at `/solo/admin`)
- Custom domain tenant (optional): `http://solo.localhost/` and `http://solo.localhost/admin` (dev; production = doctor's own domain at root paths)
- Dr. Nusrat Urmi tenant (path): `http://localhost/nusraturmi/` (book at `/nusraturmi/book`, admin at `/nusraturmi/admin`); custom domain `http://nusraturmi.localhost/` or `drurminusrat.com` when DNS points here. Seed with `php artisan db:seed --class=NusratUrmiSeeder` (includes `NusratUrmiDemoSeeder` for Daily Roster / queue demo data; re-run demo only with `--class=NusratUrmiDemoSeeder`).

Tests: `php artisan test` (SQLite in-memory). To run the suite against the production database engine:

```bash
mysql -u root -e "CREATE DATABASE soldoc_mysql_test CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
DB_CONNECTION=mysql DB_DATABASE=soldoc_mysql_test DB_USERNAME=root DB_PASSWORD= php artisan test
```

Shell environment variables override both `.env` and the `<env>` entries in `phpunit.xml`, so no config edit is needed. CI (`.github/workflows/tests.yml`) runs both engines on every pull request.

Before serving real patients, run the readiness gate as the last step of a deploy — a non-zero exit should stop the release:

```bash
php artisan app:production-check
```

It checks the settings that fail *silently*: debug mode exposing stack traces, `MAIL_MAILER=log` swallowing a locked-out doctor's password reset, `SMS_DRIVER=log` meaning no patient is ever told their serial, still running on SQLite, a non-https or localhost `APP_URL` (patient ticket links in SMS are built from it), clinical media on the server's own disk, and an insecure session cookie. Blockers exit non-zero; the two storage/cookie items are warnings unless `--strict`. Defined in `app/Support/ProductionReadiness.php`, and CI asserts the gate can still pass on a production-shaped config so it cannot drift into something nobody can satisfy.

Scheduled tasks: `commissions:generate-monthly` runs on the 7th of each month (pending monthly commission rows for referred active tenants).

## Tech Stack
- PHP ^8.3 (Composer `platform.php` = `8.3.0`), Laravel ^12, Filament ^4
- stancl/tenancy ^3.10 — hybrid tenancy: **path** on central domain (`/{tenant}/…`), **domain** for optional custom domains (root paths)
- mews/purifier ^3.4 (HTML sanitization for page builder); Filament uses `symfony/html-sanitizer` **^7.0** (not 8.x — 8.x needs PHP 8.4 `Dom\HTMLDocument`)
- Livewire (via Filament)
- Blade views for patient site, booking wizard, ticket, portal, waiting-room screen
- Vite ^7 + Tailwind CSS ^4 (front-end build)
- PHPUnit ^11 for feature tests
- SQLite locally and in CI; **MySQL in production — validated 2026-08-08**, and CI now runs the whole suite against MySQL 8.4 as well (`phpunit-mysql` job). SQLite alone had hidden three unrunnable migrations: it does not resolve foreign-key targets at CREATE time, has no `ONLY_FULL_GROUP_BY`, accepts a datetime in a date column, and serialises every write so row locks are never contended
- SMS: `log` driver (default) or `http` JSON POST gateway; prepaid wallet on `tenants.sms_balance`

- `app/Support/GsmText.php` — keeps an SMS body inside one billable segment. Networks bill per **segment** (160 GSM-alphabet characters, or only 70 the moment one character falls outside it) while credits are sold as "1 credit = 1 message". `toSingleSegment()` transliterates via `Str::ascii()` — flattening typographic dashes and rendering a Bangla patient name readably (`ফাতিমা রহমান` → `fatima rhman`) rather than deleting it — then truncates prose, never a link, to fit. `segments()` is encoding-aware (160/153 GSM, 70/67 UCS-2) so the wallet can charge what was really sent
- `app/Jobs/SendDoctorLateNotices.php` — texts every waiting patient that the doctor is running late. Dispatched from `LiveSessionService::markDelay()` with `->afterResponse()`, **deliberately not onto the queue**: this application runs no queue worker, so a queued job would never be delivered and nobody would notice the patients went untold. After-response runs in the same process once the response is sent, needs no infrastructure, and still frees the screen. Carries `tenantId` and re-initialises tenancy itself, and is `ShouldQueue`, so moving to a real worker later is deleting `->afterResponse()` (`QueueTenancyBootstrapper` is already enabled)
- `app/Casts/DateOnly.php` — custom cast for date-only columns (`Booking::booking_date`, `LiveSession::session_date`, `SlotBlock::date`, `ChamberCashEntry::occurred_on`). Laravel's built-in `'date'` cast reads back a start-of-day Carbon but writes through the model's generic datetime format on save, leaving a `00:00:00` time component that real DATE columns (MySQL/Postgres) coerce away but SQLite stores literally — `DateOnly` writes `Y-m-d` on every driver, so a plain `where('booking_date', $ymd)` matches consistently and stays index-friendly

- `app/Models/DrugInteraction.php`, `data/drug-interactions.csv`, `data/build-drug-interactions.py`, `app/Console/Commands/LoadDrugInteractionsCommand.php` — **221 ingredient pairs** expanded from 22 clinical rules, tenant-agnostic, loaded by `interactions:load` (also called from `catalogues:load`). ## Key Components
- **Tenant + plan features** (`Tenant::hasFeature`, `Tenant::maxChambers`, `Tenant::hasFrontDoor` / `hasLiveQueue` / `hasPrescription`) — `plan_tier` `solo` | `clinic` with size defaults; per-tenant `feature_flags` JSON can override. **Product modules** (sellable independently, default ON when the key is absent so existing chambers keep the full product): `front_door` (website + online booking + Daily Roster day list; ticket shows sitting name + time window only), `live_queue` (Live Queue Control, outdoor TV `/screen`, ticket live “now serving” + come-around ETA, Branding queue settings), `prescription` (Consult Screen, Rx print/share, medicines APIs, follow-up reminders, visit media). Super Admin tenant form has a **Product modules** checkbox list that merges into `feature_flags` without wiping add-ons; routes use `tenant.module:{name}` middleware (`EnsureTenantHasModule`). **Solo list prices** follow modules via `PlanPricingService::listPricesForModules` / `listPricesForTenant` (`config/marketing.php` `modules`: Front door ৳7,500/৳1,000 mo, Prescription ৳2,500/৳0, Live queue ৳7,500/৳2,000; all three bundle ৳15,000/৳3,000). Clinic tier still uses Clinic list price. Solo size defaults: `multiple_chambers` on (cap 5 via `SOLO_MAX_CHAMBERS`), no `lab_tests`, no `multiple_doctors`. Clinic defaults: all three size flags on, unlimited chambers. `bangla_homepage` is a paid add-on flag. Booking confirmation SMS stays optional (prepaid wallet + per-doctor `notify_channels`), not a module. Browser tab icon via `Tenant::faviconHref()` — custom `favicon_url`, else shared `/icons/health-favicon.svg` (`Tenant::DEFAULT_FAVICON`).
- **Marketer commissions** — `Marketer` profile linked to central `User` (`role=marketer`). - **Medicine catalogue** (`medicines` table) — tenant-agnostic, **24,491 SKUs across 16,029 brands** (the whole Bangladesh market) from `data/medicine-list-draft.csv`, rebuilt via `data/build-medicine-catalogue.py`. Columns: `brand_name`, `generic_name`, `default_strength`, `form`, JSON `aliases`, `category`, JSON `practice_types`, plus `indications` (concise therapeutic class), `manufacturer`, `is_essential` and `priority`. **One row per brand + strength + form, not per brand** — `brand_name` is indexed, never unique. NAPA is seven rows (500 mg tablet, 120 mg/5 ml syrup, 80 mg/ml paediatric drops, three suppository strengths, an IV infusion); upserting on brand alone collapsed those and silently discarded 8,656 SKUs, hitting syrups and drops hardest. `medicines_sku_index` covers the loader's upsert key.
- **Catalogue tiers** (`medicines.priority`) — the safety mechanism that **replaced leaving rows out**. `0` pinned (hand-verified household brands, strength and form checked), `1` curated (the reviewed 460 seed, kept verbatim), `2` essential (generic on the Bangladesh NEML 2016 or WHO EML 2025 → `is_essential`), `3` standard, `4` specialist (parenteral, chemo, vaccines). `MedicineService::tierBoost()` turns the tier into a search-rank bonus (32 down to 0) wider than the gap between a prefix and a substring text match, so searching "ace" surfaces the hand-verified 500 mg tablet above the IV infusion of the same brand. Everything remains findable; only the order changes. Guarded by `MedicinePickerTest::test_search_ranks_a_pinned_brand_above_a_parenteral_sku_of_the_same_name`.
- **Interaction-check feasibility** — measured 2026-08-12 with `drugs:coverage-report`, and the result gates the feature rather than describing one that exists. **There is no interaction checking in ChamberQ.** Of 24,486 catalogue rows, **92.9% are fully checkable** (every ingredient resolves), 1.6% partly, 5.5% not at all. Of what fails, 1,190 rows are devices, supplements and ORS that cannot interact anyway; **906 rows (3.7%) are real medicines absent from the US vocabulary entirely** — `doxophylline`, `rupatadine`, `bilastine`, `mirogabalin`, `roxadustat`, `cilnidipine`, `favipiravir`, `dexibuprofen`, `omarigliptin`. These fail under every spelling, are not FDA-approved, and are ordinary chamber prescriptions here. That blind spot is structural, not a data-cleaning task: any US-derived interaction database will under-warn on exactly the drugs that distinguish this market. Consequence for any future build — the screen must state which medicines it could **not** check, because a silent skip converts "no warning" into false reassurance.
- Loaded via `php artisan medicines:load` or `catalogues:load` (~12s for 24k rows, one transaction so a failed import leaves the catalogue untouched); `--prune` deletes catalogue rows absent from the CSV without touching `medicine_usages`. **Migrations alone leave this table empty** — forgetting the load step leaves prescription pickers blank with no error. `app:production-check` flags an empty catalogue as a blocker on production servers. - **Per-drug dosing defaults** (`medicines.default_frequency`, `default_duration`, `default_timing`) — layer 2 of the prefill chain, from `data/dosing-defaults.csv` via `php artisan dosing-defaults:load` (run last by `catalogues:load`, since it writes onto rows `medicines:load` has just upserted). **Not populated by `medicines:load`**: BDDrugBank is a product list and carries no dosing, and no source does — dosing is a clinical judgement, not a property of the product — so these live in a separate hand-written sheet and a catalogue refresh cannot overwrite them. 171 generics ship enabled; a row is skipped by writing `hold` in its `hold` column. Currently reaches **9,862 SKUs**. Three guard rails in the loader: values outside the pad's frequency/duration/timing vocabularies are **rejected rather than stored** (the pad renders these as chips, so a typo would be an unfixable cell); only oral forms (`tablet`, `capsule`, `syrup`, `sachet`) are touched, so an oral pattern never lands on an injection or an eye drop; and a combination product never inherits a single-ingredient default, so `Diclofenac Sodium + Misoprostol` is left alone by the Diclofenac row. - **Medicine usages** (`medicine_usages` table) — per tenant + doctor rows the doctor curates by hand: last dose/frequency/duration, `last_timing` (a `PrescriptionTiming` key, added 2026-08-12 so layer 1 can override the catalogue on the field patients most often get wrong), retired `use_count` / `last_used_at` counters, optional `hidden_at` (doctor hides from their picker without touching the shared catalogue).
- **Three-layer prefill** — the rule for every prescription cell: **the doctor's own saved default → the catalogue's per-drug default → blank**. Resolved **field by field**, not row by row, so saving a dose does not wipe a frequency he never touched, and resolved once inside `MedicineService::search()` so the Alpine pad and the Filament modal cannot drift. Blank is a deliberate third layer, never a guess: the previous behaviour hardcoded `'1+1+1'` and `'5 days'` in `MedicinePickerFields` and applied them to every drug alike, which is wrong for a PPI (`1+0+0` before food), an antihistamine (`0+0+1` at night) and anything taken long term. Both literals are gone; `RxAutomationTest::test_a_drug_with_no_catalogue_default_stays_blank` stops one creeping back.

Results are deduped to one entry per brand and capped at `MAX_RESULTS` (20); measured 5–50 ms and a single query. **There is no whole-catalogue read left in the service.** `groupedSelectOptions()`, `catalogMedicinesForPracticeType()`, `personalMedicineOptions()`, `excludeBrandsFromOptions()`, `normalizedBrandSet()`, `catalogForPracticeType()` and the `MAX_CATALOG_ROWS` cap were **deleted** on 2026-08-12: switching the picker to `getSearchResultsUsing()` orphaned the whole chain, and it could not scale to 24k rows. The generic stays in the label so searching "omeprazole" still finds OMEE (`bug_history.md`). `resolvePrescribingDoctor(?Booking)` decides whose practice type that is, in order: the booking's `ScheduleSession` doctor (a doctor covering someone else's session prescribes as that session) → the signed-in doctor's own paired profile (`User::doctorProfile`) → the single `Doctor` row of a solo practice → `null`. The middle step exists because without a booking (My medicines, bare `/api/medicines/search`) a clinic has no way to name the doctor: before it, clinic doctors silently got the general-physician catalogue while solo doctors got their own. `null` still means "no prescriber", which `User::canEnterPrescriptionFor()` treats as deny. `saveDoctorMedicine()` (formerly `recordUsage()`) is called **only from My medicines**, when a doctor deliberately saves a brand and its defaults; prescribing writes nothing. It leaves the retired `use_count` / `last_used_at` counters alone. Search ranks on text match, with the doctor's own saved entries +15 ahead of the shared catalogue — their curation, not inference. Where both a usage row and a catalogue row exist for the same brand, dedupe **prefers the usage row** rather than the higher-ranked one: a curated SKU's tier boost (up to 32) outweighs the +15 usage bonus, so ranking alone dropped the doctor's own line for exactly the brands he had bothered to save. Each returned row is already resolved through the three prefill layers and also carries `timing` and a `class_hint` (the catalogue's therapeutic class, shown in the suggestion list to confirm the right brand, never stored on the prescription). The per-row catalogue lookup inside that loop is now one batched `whereIn` (it ran per keystroke, with a patient in the room). `normalizeMedicineName()` uppercases brand names for paper-script consistency.

Start/end session, call next, call a *specific* patient out of turn (`callSpecificPatient()`), mark arrived (`in_chamber`), skip, complete (`completeCurrentPatient()` marks done **and** advances; `completeCurrentPatientWithoutAdvancing()` marks done and holds the room until `callNextPatient()` is called explicitly — same lock/transaction, used by the two-step consult flow); drives outdoor screen + Live Queue Control. `callSpecificPatient()` refuses while the current booking is `in_chamber` (a consult in progress is never interrupted) and returns a merely-`called` patient to `waiting` with `called_at` cleared and no skip strike, since being jumped is not their fault. `setAsCurrent()` clears `retry_queue_position` as it calls a patient, so a consumed retry slot cannot linger as a stale "back in queue after #N" hint. ## Data Flow
1. **Sales:** Visitor hits central `/` (optional `?ref=` / `?code=`) → WhatsApp CTA includes referral context → Super Admin creates tenant, attaches marketer/discount, snapshots pricing → pending setup commission.
2. **Billing:** Super Admin confirms doctor setup/monthly payment (manual bKash) → commission moves to `owed` → monthly cron creates pending rows → Super Admin marks marketer payout paid. **Client Health** (`/admin/seller-overview`) surfaces who went quiet, where new signups stall, SMS wallets at risk, and overdue accounts — counts only, never patient clinical data. **Research data** (`/admin/research`) shows anonymous coded-diagnosis aggregates across all practices with k-anonymity (minimum group size 10).
3. **Patient book (doctor's website):** Tenant site → the clinic hero form **POSTs** to `/book` (name/phone flashed to the session, then redirected — never in the URL) or a plain `GET /book` → wizard (chamber/doctor filters when needed, then **When can you come?** via `GET /api/bookings/open-dates` — only open dates with seats, soonest first; short identity step (summary strip, then details; **Change date** on the summary strip (or Back))) → `GET /api/bookings/availability` (re-check before submit) + `GET /api/patients/by-phone` (public, throttled 10/min, masked initials only) → `POST /api/bookings` (optional `patient_id`, `share_clinical_history` 0/1 defaulting on, optional `nid`; optional `wants_earlier_date` still accepted by the API but not collected in the wizard) → `BookingService` creates booking + patient link inside a DB transaction with `lockForUpdate()` on the bookable (and doctor row when `slot_cap_mode` is `per_doctor_chamber`) → after commit, `SmsService` debits wallet and sends confirmation naming the patient (SMS ticket link from `APP_URL` / custom Domain) → JSON `ticket_url` is a **relative** path so the wizard redirects without baking in a wrong host → ticket (share via WhatsApp/copy, or Print / Save as PDF via the browser print dialog). Staff may still follow up on any legacy `wants_earlier_date` rows from **Waiting for earlier date**. A ChamberQ patient login on the same host prefills name/phone; booking still does not require it.
3b. **Patient book (ChamberQ Find):** Central `/find` (public directory) → Book serial on `/{tenant}/book` (same `BookingService`) → ticket on that doctor's site. Optional `/me/login` (phone OTP) unlocks `/me` (upcoming serials across clinics) and `/me/history` (own visits + prescriptions, no share-flag gate, no media).
4. **Clinic day:** Staff or doctor (per `queue_runner`) open Live Queue Control → start session → call patients → Patient arrived (`in_chamber`) → complete (doctors get optional visit-notes modal with voice/photo; staff complete without notes). Patients can also be called out of turn from their table row, and a no-response skip is taken from the current-call card with its consequence spelled out on the button. Doctor Consult Screen auto-follows `current_booking_id` for clinical context including last visit notes. Live Queue Control shows an amber catch-up banner when completed patients lack notes (**Fill in now**). End session names how many patients it is about to cancel and who, then hands staff a WhatsApp link per cancelled patient; it also warns doctors if notes are still missing and points them at **Fill in now** on the same page. Daily Roster is a second entry point (walk-ins, roster view, **Mark Late** before Start, **Collect fee** for the desk khata); call/complete/Mark Late actions only for the queue runner. End-of-day money is **Operations → Cashbook** (income, expense, net, waived). For a doctor who prescribes on paper and has switched `staff_may_enter_prescriptions` on, staff get an extra **Enter prescription** action on that doctor's *completed* roster rows: they photograph the slip, type the medicines and follow-up, and the visit gains a prescription with no status change and no doctor approval step — staff still see no diagnosis, voice note or visit history. Both screens route through `LiveSessionService`, so outdoor screen and ticket stay in sync. Outdoor TV polls `/api/screen/{session}/{date}`. Ticket page polls `/api/queue/{booking}` — neither exposes visit notes or media paths.
5. **Writing the prescription (desktop, mid-consult):** Doctor opens the Rx pad → C/C as complaint rows (each with its own duration), H/O already seeded from the patient record, vitals typed fresh with last visit's shown grey beside them → picks a diagnosis, which offers his own packs for it plus shipped advice/investigation presets → types a brand, and the row's dose, frequency, duration and timing arrive already resolved through his own saved default, then the catalogue's, then blank → ★ saves that line to **My medicines** (packs themselves are built there, not here) → **Save** posts once via `ConsultScreen::saveRxDesk()` → `VisitRecordService::saveForCompletedBooking()` without ending the visit. Every one of those fills is a proposal on a document the doctor signs: visible, editable, and cleared in a keystroke.
6. **Lookup:** Patient opens `/portal`, enters phone → exact-match booking list (throttled) **and** up to two recent prescriptions with medicines (View prescription → phone-gated full pad). Fully translated for Bangla, as are the wizard and ticket — `PatientFacingBanglaTest` fails the build if a patient-reachable string has no `lang/bn.json` entry. The staff/admin panel is deliberately English-only (see `decisions.md` 2026-08-08).
7. **Content:** Admin structures WebPages; staff edits text/images; public `/{slug?}` renders tenant site.
8. **Labs (clinic tier / flag):** Patient can add lab tests + collection slot during booking; ops manage LabTests + LabCollectionSlots in admin.
9. **Chamber outage:** Doctor already has Consult Screen open → line drops → yellow banner → pad Save/Print stay on this computer (`rx_save` in IndexedDB) → Call next / walk-ins freeze → when the line returns, `POST /api/offline/sync` uploads notes onto the existing `in_chamber` booking without advancing the queue.
10. **Visiting / camp day:** Night before, doctor taps **Pack bag** on **Operations → Visiting / camp** → at the remote room they add walk-ins and print from the laptop → pending `visiting_visit` items upload when signal returns (SMS only after that).
